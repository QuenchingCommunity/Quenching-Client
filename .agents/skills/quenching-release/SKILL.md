# 淬火版本发布

以当前源码、客户端 assets、Latest 资源 Git 历史和本次候选产物为依据；历史发布只按需取回所需文件，不常驻保留每版完整旧包／旧树。历史对话和旧发布脚本提供线索，不能代替本次产物验收。任务只要求“准备”时，停在候选产物及交接单；不自行上传、替换线上清单、打开门禁或删除远程资产。

## 先读取

- 客户端资源准备／打包入口维护：先读 [统一资源源目录与按需 7z](references/resource-bundle.md)。2026-10-28 最新源为 `assets/unpacked`，分发五个按素材种类固定分组的独立 `resources-*.7z`；旧 shader ZIP 和 UI 独立 ZIP 描述按历史方案理解。

- 每次发布：先读 [测试优先流程与资源／Git 历史](references/test-first-workflow.md)，按“带标记本地包 → 用户人工通过 → 独立测试自动更新 → 用户再次通过 → 正式大包及验证”执行；再完整阅读 [准备与验收清单](references/preparation.md)，按其中的输入表建立本次记录。
- 每次版本变化同时核对 [UIQUE／WebUI 版本文字](references/version-assets.md)：根 `release-version.json` 统一对外版本，构建生成 HTML 和两份 UI ZIP 的八处字段；还须验证版本 String 的字体及父级 `DecorateFileNames`，不能只搜到版本字符串就判为可见。中英文 PNG 不再带版本，不每版重做图片。
- 生成产物或交接网站：阅读 [协议、代码与工具位置](references/contracts-and-code.md) 的对应章节，核对源码中的实际参数、路径和协议。
- 涉及跨版本更新：阅读仓库 `wiki/file-sync-updates.md`；涉及已分发 3.5／3.51：同时阅读 `wiki/3.51-client-bugfix-verification.md` 中的发布验证、基线调查和未发布改动。
- 涉及 MOD 后续资源更新：阅读 `wiki/mod-zip-updates.md`。2026-10-09 用户决定 MOD 改为逐资源版本普通 ZIP，客户端保留已验收的按文件差异更新；旧同协议描述仅作为兼容历史。
- 实现代码修改时，另遵循仓库现有项目指引；本 skill 不授权顺带重构客户端。

本文及 references 中的代码路径均相对仓库根目录，不能相对当前 skill 目录执行命令。

## 决策顺序

1. 确认本次只是修改流程、阶段 A 本地测试、阶段 B 测试更新，还是已满足两次人工验收后的阶段 C 正式准备／发布；记录真实内部版本和本次授权。流程修改不自动开始打包或发布。
2. 核对两个仓库：当前客户端源码及 `assets/`；`D:/Quenching/QM/Latest` 是独立 Quenching-Assets Git 工作区。记录前版／目标 commit、未提交变更和小型发布元数据，不另外复制整套旧资源／旧客户端常驻。Git 缺少某个已发布版本的提交时明确记录缺口，不能拿当前 HEAD 冒充；客户端旧二进制需用时按原哈希从 Release 取回，不假设重编译相同。
3. 完整包／MOD 新资源只读取 Latest；客户端自身附加资源只读取仓库 `assets/`。不创建历史 `mod-root`／全量冻结树，不在打包时拿 assets 临时覆盖 Latest。详细入口见 [Latest 唯一源流程](references/latest-source.md)。
4. **阶段 A**：首次本地便携导出就携带 EXE 同级 `quenching-update-test.json`，指定本次独立测试 base；验证无环境变量时直接双击可见、配置隔离、测试失败不转正式。交给用户人工测试，等待其对该候选明确通过；此前不制作本次测试自动更新、正式大包或正式更新。
5. **阶段 B**：第一次人工通过后，才制作真实递增内部版本／MOD sequence 的测试自动更新，使用独立测试签名索引和 store；旧已验收测试安装升级后仍保留标记。交用户再验证下载、安装、退出、自动重启与设置，等待第二次明确通过。
6. **阶段 C**：两次人工通过后，才制作正式 Win／Mac 大包、需要的 MOD A／B 和正式更新清单，去除测试标记／配置，验证正式链路。代码、资源、版本变化重做相应验收；正式上传／部署／开放门禁仍须符合本次发布授权。
7. 按变更范围制作，不把客户端升级误当成 MOD 升级：

| 本次范围 | 客户端 | MOD 更新与完整包 |
| --- | --- | --- |
| 仅客户端修改 | A 的 TEST 便携 ZIP；B 的测试自动更新；C 的正式 Win／Mac ZIP 与 Windows 清单 | MOD 版本、sequence、正式索引和原完整包不变，不造空资源补丁 |
| 仅 MOD 修改 | A 用带标记客户端人工测试；客户端源码版本无变化时不凭空发布新客户端 | A 本地资源候选；B 独立测试 ZIP 链；C 正式资源更新，按需要制作首装 A／B |
| 客户端＋MOD 修改 | 按 A／B／C 执行 | 同阶段执行资源候选／测试更新／正式更新；同时更新先 MOD 后客户端 |

8. schema 1 旧桥、客户端 schema 2 文件同步与 MOD schema 3 连续 ZIP 分别验收；旧代码不会因服务器换索引学会新协议。逐源实际下载核对字节，保留小型清单／哈希／Git 映射和验收记录；可重新获取的大对象用完释放，不每版累积完整旧树。

## 必须保留的项目约束

- 用户 2026-10-26／28 更新要求：保留魔兽 2.04（2.0.4）、3.0（3.0.0）和“最新（3.01）”（3.0.1+），并保留自动检测。3.0 的原字节独立兼容源目录放在 `assets/unpacked/shaders`，Win／Mac 通过固定分组的五个独立 `resources-*.7z` 分发，不再分发独立 legacy ZIP；不能以新版着色器重做旧 ABI。2.04／3.0 屏蔽本轮新增辨识度、增强描边和单位缩小，原有基础效果继续保留；2.04 仍不支持 DE。详见 `wiki/war3-version-feature-matrix-20261026.md`。不重新打包 shaders136 / shaders200。
- 当前发布主源是 **GitHub Release＋官网清单控制的备用镜像**；两产品分仓库。GitLawb 已因持续失败被用户停用，不作为发布必需项；不是 GitLab。Irys 当前停用，`_irys/` 只是既有私有发布工具目录名。R2 是私有 Worker 最后备用，须实际验收对应传输后才能启用。
- 用户 2026-10-28 更新要求：不提供安装程序；客户端便携导出统一 7z，Mac 使用 tar.7z 保存签名包的链接、权限和扩展属性。历史客户端 ZIP 及更新协议继续兼容读取。完整包 A／B 是两个可分别解压的普通 ZIP，不能制作需要拼接的 `.001/.002` 分卷。自动更新传输的内部分片是另一回事。
- 内部客户端 `3.5.1` 对应用户口中的 `3.51`，对外可仍显示 `3.5`。新内容要用更高的内部版本；不能重建同一个内部版本并期待已装该版的玩家收到更新。
- 资源版本读取分支 `_patch/keep.que`；没有新标记时，3.4 仅用 `Rbuildings`、`RetroTex`、`RUnits` 三个固定目录识别，各自可以在该分支根或其 `QMoff`。保留 `_retail_`、`_ptr_` 下划线。
- 自动检查在启动约 10 秒后，只读小型索引和版本标记。文件清单用于发布元数据比较，不用于扫描玩家目录猜版本或强制玩家目录 100% 等于标准包。
- 用户确认前不下载／安装。MOD 与客户端共用一个确认弹窗，显示当前和目标版本；同时更新时先资源包，再客户端。
- 不能因新清单里没有某文件就删除玩家文件。开启 MOD 不要求完整包、标记或所有权清单齐全。已明确由客户端管理的当前分支 `ui` 可重置，这不扩展到其他目录。
- 客户端源 `assets/` 一律复制，不移动。发布准备不得反向修改 `assets/quenching` 来适配 QMF，也不默认用客户端 assets 覆盖 Latest。用户明确要求对齐时，先作为资源编辑复制到 Latest 并核对；发布工具仍只读取 Latest。玩家自定义、原导入文件、另一分支和设置必须保留。
- 客户端保持当前／最新官方快照比较，EXE／ASAR 可选差分、失败回退目标单文件；其他变化资源整文件。MOD 改为相邻官方资源版本各一份普通 ZIP，官网签名 schema 3 索引控制连续更新链、源和步数上限（默认 6）。每步独立提交／失败回滚，不强制玩家旧目录符合清单；不再为新 MOD 发布逐文件对象。签名和下载哈希仍验证。
- 不擅自升级 Electron。当前自动更新仅 Windows x64；内核／核心变化走新便携包。macOS 仍手动更换，不给它 Windows 清单。
- `_irys/`、`.env`、上传身份和签名私钥不进入 Git、客户端、ZIP 或公开清单；客户端只带公钥。历史资源由 Git commit/tag 追溯，保留小型官方清单、签名索引、产物哈希／URL；仍被签名索引引用的远程资产保留兼容。旧 ZIP／EXE／ASAR 只在本次验证需要时取回，不要求常驻备份；移除现存缓存前核对可重取性与工具依赖。
- 官网元数据保持 `qm.txzy.net`，旧域兼容另核对；客户端埋点仍用 `https://qm.txzy.net/v1/telemetry/events`，不要因为后端迁移修改客户端 URL。
