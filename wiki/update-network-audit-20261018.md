# 自动更新直连审计（2026-10-18）

## 结论与边界

不是“所有镜像都没有效果”。当前新版传输链路的 GitHub、gh-proxy.com、ghfast.top 在本机可用，真实 Windows 更新下载器也完成了低速切源和完整大文件校验。gh-proxy.org 明显不稳定。

同时发现独立于大文件镜像的风险：官网清单／快照连接和传输间歇失败；旧域门禁仍是 3.4；旧 3.5 客户端的桥接下载表与新版镜像策略不是一回事。不能把新版下载通过等同于每个旧客户端都能顺利升级。

本轮只读线上内容，新增私有诊断脚本和本报告；没有改客户端实现、版本、资源、签名清单、官网、DNS 或系统代理，没有上传 R2 或运行真实游戏、安装／替换客户端。诊断脚本全部在忽略 Git 的 `_irys/`，详细原始结果在 `_irys/work/network-20261018/`。生成的临时下载文件用后删除，没有额外保留完整资源树。

## 网络环境

- Windows 系统代理仍配置为 `127.0.0.1:4444`，没有为测试关闭或修改它。
- 测试用原生 Node HTTPS 显式直连 Agent、Windows curl `--noproxy '*'`，不走该 HTTP 系统代理，也没有关闭 TLS 验证或使用第三方镜像转发元数据。
- 默认 IPv4 路由是普通物理网络到本地网关，未见接管默认 IPv4 路由的 VPN 路由。不能仅据此排除网关之外的所有网络设施。
- 直连 Cloudflare trace 返回 `loc=CN`、`warp=off`、`colo=LAX`。没有保存或展示访问者公网 IP。这是本机大陆出口样本，不是全国各地区／运营商保证，也不是大陆 CDN 节点的证明。
- 网络矩阵使用本机 Node；另用实际 Windows Electron **33.1.0 / Node 20.18.0** 运行生产下载器和门禁实现，避免只用独立 Node 的结果代替客户端运行时。

## 线上版本及签名

- 客户端 schema 2 targetVersion **3.6.1**，runtimeVersion **33.1.0**；API／非 API latest.json 取得的字节一致，公钥验签通过。
- MOD schema 3 **3.6.2 / sequence 38**，4 段 ZIP：3.4→3.5→3.6→3.6.1→3.6.2；取得的清单验签通过。
- 新版两种清单的镜像顺序均为 GitHub → gh-proxy.com → gh-proxy.org → ghfast.top；没有 R2 下载源。
- 客户端比较 3.6.0 与 3.6.1 官方快照，确认为 8 个变化文件，另有 2 份可选二进制差分。目标／旧快照真实下载后都完成大小与 SHA-256 校验。
- 快照第一轮请求全部失败时，仅用本地留存的、哈希与线上签名完全相同的正式快照规划测试；这不计为网络成功。后续矩阵确实重新下载并校验了网站快照，结果分别保存。

## 新版下载源矩阵

14 项 Release 资产 = 4 份 MOD ZIP + 8 个客户端变化整文件 + 2 份客户端差分。另测 3 个官网快照 URL，共 **59 个源／文件组合**。

| 源 | 第一轮通过／总数 | 完整 SHA-256 校验 | 大文件前缀 | 失败 |
| --- | ---: | ---: | ---: | ---: |
| GitHub Release | 14/14 | 11 | 3 | 0 |
| gh-proxy.com | 14/14 | 11 | 3 | 0 |
| ghfast.top | 14/14 | 11 | 3 | 0 |
| gh-proxy.org | 4/14 | 4 | 0 | 10 |
| qm.txzy.net 快照 URL | 3/3 | 3 | 0 | 0 |

三个大文件是约 392 MiB 的 3.4→3.5 ZIP、约 180 MiB 的 EXE 和约 76.5 MiB 的 ASAR。矩阵先检查前 8 MiB，三家成功源的前缀一致；不拿前缀代替完整性。随后在真实 Electron 下载器中，**gh-proxy.com 的三个大文件全部完整下载并通过 SHA-256**，补齐该源全部 14 个资产的整文件证据。

gh-proxy.org 的 10 次失败为低速／无进展切源；另外 4 个较小文件成功。它可以保留为靠后备用，不能当稳定主源，也不能说它所有文件均不可用。上表是这一轮样本，不是服务商长期 SLA。

原始记录：`asset-results.json`、`planned-artifacts.json`、`native-runtime-results.json`。

## Windows 生产下载器实测

使用 `src/Main/services/update-download.ts` 原实现，正常生产 15 秒策略，没有修改客户端下载函数。只给测试进程独立临时输出，不启动应用界面或更新助手。

| 文件 | 实际完成源 | 完整字节数 | 耗时 |
| --- | --- | ---: | ---: |
| 3.6.1→3.6.2 MOD ZIP | GitHub | 4,244,145 | 3.17 秒 |
| QMClient.exe | gh-proxy.com | 188,838,400 | 37.15 秒，包含前面 GitHub 低速等待 |
| app.asar | gh-proxy.com | 80,203,029 | 11.10 秒 |
| 3.4→3.5 MOD ZIP | gh-proxy.com | 411,060,215 | 48.04 秒 |

全部通过签名元数据规定的大小／SHA-256。EXE 的 GitHub 请求真实触发 SlowUpdateDownloadError，随后镜像完成下载；验证成功后，ASAR 与下一份 MOD 自动优先使用同一镜像，证明跨文件记住成功源仍有效。

另外在隔离队列开头注入一个故意拒绝连接的本机 URL，随后成功使用真实线上源，仅用于验证失败后继续下载；该 URL 没有进入线上清单。没有向第三方源发送私钥、PAT、Cookie 或 R2 凭据。

`node --import tsx scripts/test-update-download.ts --production-window` 通过：实际低速中止 **15118 ms**，以及无响应头、停滞、快／小文件、最后备用源、重定向边界、校验失败、镜像优先级及策略重置回归。没有为测试修改生产策略。

## 官网元数据是另一条可能断掉的链路

初次原生直连请求 14 个元数据入口，9 个出现连接／握手／传输超时。后续有些相同 URL 成功，所以不是宣称它们永久 404 或清单签名坏了。旧域纯文本 v3.4 在通用 JSON 探针中最初被标为解析错误，随后用真正客户端 parseReleaseGate 验证：它是合法旧格式，不是客户端 JSON 解析缺陷。

真实 Electron / Node 20 的额外观测：

- 主域 version.que 两次为 `{version:"v3.6",modVersion:"3.6.2",allowed:1}`，约 1.1–1.7 秒；实际 fetchReleaseGate 两次选择主域成功。
- 旧域 `https://www.tianxiazhengyi.net/version.que` 多次为纯文本 **v3.4**，约 0.3 秒，parseReleaseGate 得到 modVersion=3.4、allowed=1。
- 3.5.0 兼容清单 API 完整取得 49,597 字节、目标 3.6.0；另一次非 API 入口只收到 7,376 字节就停滞超时。
- 3.5.1 兼容清单非 API 完整取得 40,032 字节、目标 3.6.0；API 一次收到 32,377 字节后停滞超时。
- latest.json 一次 TLS 以后无响应至总时限，旧快照另一次 TCP 已连但 TLS 未完成。不能把这些全部归为 Worker 业务代码或全部归为文件缺失。
- curl 不走代理，也出现相同域一次连接失败、另一个入口 200 并完整接收的混合结果。

代码路径：`release-gate-service.ts:46` 顺序尝试两个域；`mod-update-service.ts:430` 读取门禁，`:432` 要求 gate.modVersion 等于 manifest.displayVersion。**如果主域门禁超时而旧域 v3.4 成功，MOD 3.6.2 会被以“门禁版本不匹配”拒绝**。观测到了这个条件所需的两个事实，源码条件也明确，但没有断言每位反馈玩家都走了这一条分支。

这是“有镜像仍不起效”的一个具体解释：检查更新和下载快照先于文件下载，第三方 GitHub 镜像有意不代理门禁／清单。这些前置请求失败时不会开始文件镜像切换。API／非 API 两个路径又都在同一 qm.txzy.net 上，不是独立网络备用。

本地网站目录的旧客户端清单实际存在，路由使用静态 ASSETS；没有证据证明 3.5 升级入口被永久移除。本轮仅检查涉及的静态路由，不重构或部署 Worker。记录见 `metadata-results.json`、`metadata-retry-results.json`、`gate-runtime-results.json`、`legacy-metadata-native-results.json`。

## 旧 3.5 客户端不能与新版镜像策略混为一谈

两份兼容清单都用客户端现有公钥验签通过：

- 3.5.0→3.6.0：schema 1，62 个文件，总签名 artifact 字节 232,693,851。
- 3.5.1→3.6.0：schema 1，50 个文件，总签名 artifact 字节 132,509,148。
- 两者没有 githubMirrors；各文件显式源为旧数字 tag `3.6` 的 GitHub Release 和 GitLawb。不能指望给新版 latest.json 调镜像就改变旧 updater 这两张下载表，也不能让旧代码直接理解新协议。

对旧数字 tag 的首批 18 个 GitHub 文件，3 个完整校验通过、15 个连接或传输超时；同批 GitLawb 的 EXE／ASAR 2 个样本反而完整校验通过。连续同类超时后停止了批量测试，保留结果，**没有把尚未测试的全部 112 个旧文件记成通过**，也不因以前停用 GitLawb就伪造其当前探测失败。后续只做有界的旧版 EXE／ASAR 与候选镜像复测，见 `legacy-fallback-results.json`。

有界复核结果：3.5.0 与 3.5.1 的 EXE／ASAR 共 4 份小型差分，在 gh-proxy.com 和 ghfast.top 共 **8/8 完整校验通过**；GitLawb **4/4** 样本通过。对应 GitHub 原链接 4 个样本仅 1 个通过，3 个超时。这不代表 GitLawb 全部旧资源或大容量服务已经重新验收，也没有重新启用其新版发布。候选镜像 URL 尚未加入旧清单，所以测试成功不等于现有玩家已经会使用它们。

旧版升级应优先在对应 schema 1 清单中显式加入经验证的镜像 URL，并用同一发布密钥重新签名；保留旧目标、基线规则、目标字节及回滚语义。此项是建议，不是本轮已部署。真正老客户端的二进制基线、安装、替换和重启并非这次网络审计的已验收范围。

## R2：可选，但本版不是已启用的救援源

现行客户端／MOD 索引未包含 R2。当前下载器只支持普通 HTTPS 字符串和分片源、只发送 User-Agent，未见私有 R2 授权握手；本工作区也没有找到可对最新对象进行验收的 R2 下载入口／授权配置。不能凭历史旧补丁测试宣称本版 R2 已经接好，更不能凭缺少本地配置断言远端桶一定不存在。

网站现有 `qm-forum-media` 是论坛 MEDIA 绑定，不是客户端更新桶；没有读取它的对象、调整它的公开权限或占用它做测试。

建议的最小接法（尚未实现／上传／部署）：

1. 私有更新桶或明确隔离的更新命名空间；发布端上传签名清单真正引用的最终字节，URL 不可变。不要挪动论坛媒体。
2. 一个小 Worker，保留既定共享客户端密钥防普通滥用的边界，按 IP 每 10 分钟最多 5 次**授权**；每次更新取得一次短期授权，后续多个文件复用。不要把 8 个变化文件分别计为 8 次授权而锁死正常更新。共享密钥不是“无法被无头模拟”的保证。
3. Worker 流式传输对象，保持大小／SHA／签名校验；限路径、禁止任意 URL 转发，不公开桶。需实现并验收相应客户端授权逻辑，不能只把一个受保护 URL 塞进旧清单期待旧程序会登录。
4. 客户端仅放最新需要的整文件／可选差分和官方快照。MOD 必须同时放当前支持链路需要的 ZIP：旧用户不一定能只用最新的 4.05 MiB ZIP；3.5 用户仍需前面 3.5→3.6 等步骤。无需为此上传整个首装 A/B。
5. 验收授权成功／错误密钥／超限／授权过期、全部主源故障后的 R2 回退、真实文件完整 SHA，以及不同大陆网络。发布前不计入可用源数量。

仅加 R2 大文件不会解决门禁／快照本身不通，仍需独立元数据备用。R2 国际网络也不能承诺大陆必快；Cloudflare China Network 是独立服务，不等同普通 R2。

费用只按当前官方文档评估：Standard 存储每月免费 10 GB-month、A 类 100 万、B 类 1000 万次，出站流量免费；超额存储 $0.015/GB-month。Worker 另计，官网现有用量也应纳入预算，不保证账户总账单为零。

官方依据：[R2 价格](https://developers.cloudflare.com/r2/pricing/)、[Workers 价格](https://developers.cloudflare.com/workers/platform/pricing/)、[Cloudflare 中国网络](https://developers.cloudflare.com/china-network/)。

## 建议处理顺序

1. 先修元数据可达性和门禁备用不一致：同步或提供专用新门禁备用，兼顾仍需纯文本入口的 3.4；不要直接改签名清单字段。
2. 新镜像策略建议 com→ghfast→org，org 保留靠后；旧 schema 1 兼容下载表另行显式增加验证好的镜像并重签，不破坏旧版 URL。
3. 再接独立的 R2 更新源及授权。单独验收，不借用论坛媒体或历史原型成功记录。

这不是发布指令。本轮线上字节及客户端实现保持原样。
