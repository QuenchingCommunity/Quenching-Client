# CN1 发帧延迟优化与抖动排查（2026-10-27）

## 已上线的调整

新机仍为 `191.40.41.124`，入口仍为 `https://qmapi-cn1.txzy.net`，DNS only。服务器发帧周期由 100 ms 调到 **30 ms**。GUI 无需更新，新匹配自动使用新配置。

旧程序默认 100 ms 未全局修改；配置新增 `tickMs`，允许整数 25–250 ms，省略时兼容原来的 100 ms。仅 CN1 配置为 30 ms。双人和单人测试路径均传递该配置，健康检查返回实际周期。

为避免缩短周期导致抗抖动窗口意外缩小，最大领先帧数按 `ceil(2000/tickMs)` 设置：100 ms 是 20 帧，30 ms 是 67 帧。没有更改地图、位置、动作内容、动作顺序、校验或结算规则。已有正常退出后的在途尾包现在会被忽略，避免误伤仍在对局里的另一人。

## 原因与测量

66 ms 是网络/应用层包往返，不包含等待下一次发帧。原来每 100 ms 汇总操作一次，单次操作会增加 0–100 ms 的排队时间，不能把这个周期和网络 RTT 混为一谈。

同一台本机、同一香港源站、正常校验证书，通过真实 WSS 发送 W3GS 操作、接收广播并持续确认帧。以下都是**协议模拟客户端**；不是游戏画面上的 Ping，也不是另一位玩家的线路保证。

| 测量 | 旧 100 ms（40 样本） | 最终 30 ms（120 样本） |
| --- | --- | --- |
| 普通应用回送中位数 | 70.5 ms | 70.0 ms |
| 操作经发帧后回送中位数 | 153.7 ms | 90.6 ms |
| 操作回送 P95 | 280.3 ms | 192.8 ms |
| 操作回送最大值 | 396.5 ms | 458.6 ms |

网络状况在不同测量时段有变化，不能把 P95、最大值变化都归因于代码。第一轮 30 ms 的 40 个样本曾测到中位数 73.3 ms；最终扩大样本后为 90.6 ms，**应以最终结果和后续真人对局为依据**。

最终对局服务器诊断：

- 操作在节点中排队：中位 18.1 ms，P95 26.6 ms，最大 30.2 ms。
- 定时器延误：P95 1.0 ms，最大 1.7 ms。
- 等待客户端追帧造成的暂停次数：0。
- 两条 WSS 实际远端均为 `191.40.41.124`；949 个同步帧、1890 个确认，服务器协议错误 0，正常退出。

因此，软件的发帧排队已经显著下降；公网链路尖峰**没有完全解决**。不能宣称游戏稳定为 66 ms。

## 公网抖动证据与限制

独立 120 次应用回送：中位数 63.5 ms，最大 1299.2 ms，多次出现 372–684 ms 尖峰。该测量不经过游戏帧队列。

另一次 25 包 ICMP 测试，源站 3 包未返回，其余平均 60 ms；同时本地网关 25/25 返回，平均 5 ms、最大 34 ms。服务器实际 TCP 连接也观察到重传；虚拟网卡接口计数未见接收/发送丢弃或错误。ICMP 可能受限速，此小样本不能解释为长期固定 12% 游戏丢包率，也不足以断言哪一跳是故障点。

Traceroute 经过多级内网/运营商节点，中间存在不响应探测的跳点；不响应本身不等于转发丢包。现有证据支持继续定位本地公网、运营商与机房之间的线路抖动，尚不能指认具体责任方。调整程序发帧不能保证消除这些网络尖峰。

后续真人对局可直接从服务器区分：WSS RTT、原生游戏包 RTT、节点操作排队、定时器延误、追帧暂停。若 WSS RTT 本身同步升高而节点排队和定时器稳定，应优先做线路对照，而不是继续盲目缩短游戏周期。

另发现本地路由器 DNS 的 AAAA 查询曾返回旧 Cloudflare IPv6 地址；两台权威服务器和 1.1.1.1 均已无 AAAA 记录、A 记录为香港源站，属于本地解析残留。最终测量的 WSS 已明确连接 IPv4 源站，因此这些实测尖峰不能归因于旧 IPv6 入口。源站自身通过普通域名访问 HTTPS 也为 200、远端 IP 正确。本次没有修改玩家全局 DNS 或 IPv6 设置。

## 自动诊断

- 原生 W3GS Ping 每秒一次，匹配回复后记录 RTT；存在未回复 Ping 时保留等待，避免覆盖长延迟样本。
- WebSocket Ping 每五秒一次，记录独立传输 RTT；仍保留约 60 秒存活检查容忍度。
- 每个指标最多保存最近 256 个样本，保留累计次数与生命周期最大值。
- 节点时序快照每五秒记录，最多最近 120 份；结束时追加最终快照。
- 保存到已有 `/var/lib/quenching-match-player-301-lab/<gameId>.json` 的 `timings`、`wireRttMs`，不记录游戏操作内容、票据或凭据。

## 真人双端反馈：200–300 ms 尖峰

2026-10-27 用户再次报告延迟尖峰。读取当前生产实例 `d8ccca2d-f196-47c7-a324-a46fb05d6d29` 的真实双端对局 `f3b3c704-c624-49ac-8dde-435acf7fa725`：北京时间 19:52:38 开始、20:16:27 双方离开，服务记录没有协议错误。排查只读取报告和系统状态，没有重启服务或部署聊天修复。

| 指标 | 玩家 1 | 玩家 2 |
| --- | --- | --- |
| WSS RTT 中位数 | 53.4 ms | 31.7 ms |
| WSS RTT P95 | 174.0 ms | 311.1 ms |
| WSS RTT P99 | 894.8 ms | 869.4 ms |
| WSS RTT 全局最大值 | 2037.5 ms | 929.1 ms |
| 原生 W3GS RTT 中位数 | 55.2 ms | 29.6 ms |
| 原生 W3GS RTT P95 | 437.2 ms | 446.9 ms |

各项百分位来自各自最近最多 256 个观测值，采样频率和覆盖时段不同，不能当作整局百分位，也不能把 WSS 和原生 RTT 逐行相减。最大值是整局累计最大值。

发帧定时器整局最大迟到 **6 ms**，最后窗口 P95 为 **1.4 ms**。操作排队最后窗口中位数 **14 ms**、P95 **29 ms**，但整局最大值曾达到 **1451.6 ms**；不能说整个对局的节点排队始终只有 30 ms。累计出现 **62 次等待客户端帧确认的定时周期**，最后保留的快照也记录到多次确认等待，因此严重链路/客户端停顿会进一步阻塞两人的同步。没有通过增大缓冲窗口或丢弃操作来掩盖这些停顿。

独立于游戏原生处理的 WSS Ping 本身已出现较大尖峰，因此“只有游戏发帧周期太大”无法解释当前问题。现有证据指向传输路径或客户端桥接进程调度的抖动；缺少本局逐连接重传与客户端时序记录，暂不能把原因明确归到 TCP 丢包、某个玩家的 Wi-Fi、某个运营商或机房。排查时系统负载约 0.04，短时间采样 CPU 空闲 96–100%，这只是排查时状态；整局定时器记录对排除长期节点事件循环阻塞更有价值。

代码核对：本机游戏 TCP 已启用 `setNoDelay(true)`；WebSocket 库也启用 TCP_NODELAY；两端消息压缩关闭；Nginx 的代理请求缓冲和响应缓冲均关闭。无需把这些已经生效的选项再当成新增优化。主机累计重传计数没有本局连接归属，不能作为本局丢包率。

后续应对游戏传输进行抗抖动改造与真实线路对照，而非继续盲目缩短 30 ms 周期。已有 QUIC/DATAGRAM 副本实验仍是独立实验，**尚未接入 GUI 或生产节点**；其受控丢包结果不能承诺会消除这次公网尖峰。接入前仍需完成票据认证、可变长度 W3GS 封包、保序去重、可靠尾包和旧 WSS 回退，再做双端真实地图验收。

证据：[真人对局尖峰摘要](evidence/matchmaking-cn1-real-game-spikes-20261027.json)。这些是服务器测得的 RTT，不等同于魔兽画面上的 Ping。用户此前要求等其通知对局结束再重载，虽排查时健康检查显示空闲，本次仍未自动执行部署。
