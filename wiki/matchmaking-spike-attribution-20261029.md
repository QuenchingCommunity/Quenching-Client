# r9.5 瞬时延迟调查

调查时间：北京时间 2026-10-29 02:35 起（UTC 2026-10-28 18:35 起）。保留线上 r9.5，未重启在线匹配、QUIC sidecar 或 Nginx。

## 当前判断

证据不支持“服务器 CPU 不够，换更强机器即可解决”。异常涉及受损传输的恢复等待；我们的实现也有明确恢复缺陷。暂不能把物理故障进一步定位为玩家接入网、跨网线路或服务器供应商网络。

不能把 QUIC ACK RTT 低理解为游戏数据已经准时交付。已经确认抵达的包可以很快往返，而先前缺失的游戏字节仍在等重传。应用要求按序交付，后续数据因此等待；单条 QUIC stream 同样可能发生这种等待。

## 真人对局

gameId：`e05ecdeb-d8c4-4594-876a-4f24241be872`。双方上报 `transport-quic`，本机完成报告 build 为 `2026.10.29-replay-quic-seed`。

读取时一端原生 RTT 最大 8354 ms，另一端 84.9 ms。服务器帧调度延后最大 18.1 ms；操作排队最大 5697.8 ms；累计等待同步 418 个 tick。418 是等待计数，不是 418 次独立卡顿。

sidecar 在这局结束附近输出两条关闭统计，分别发送约 5.8 万帧。一条 `frameSendMaxUs=6865710`（约 6.866 秒），对应 `lockWaitMaxUs=48`；另一条发送最大约 2.108 ms。尚无连接 ID 把每条关闭统计严格映射到 playerId，但它们对应此时唯一真人对局的两条连接。本机 helper 最大发送耗时约 8.444 ms。

这确认有一条服务端传输写入长时间等待，不能把它称为服务器事件循环卡了 6.8 秒，也不能仅凭该统计断言写入为何阻塞。流量控制、拥塞与传输恢复、接收端读取停顿均可能参与。

服务器当时负载约 0.1，CPU 采样约 96–99% idle；系统 UDP 接收错误、收发缓冲错误计数均为 0，虚拟网卡错误/丢弃计数为 0。这不排除虚拟机外部或运营商链路丢包。

用户反馈画面和操作一起停，与锁步同步等待相容；不能据此直接归因渲染卡顿。

## 公网对照

不启动、操作魔兽，仅用 W3GS 合成端和交付 helper 连接同一节点：

| 对照 | 原生协议 RTT 最大值 | 服务端计时器最大延后 |
|---|---:|---:|
| QUIC 90 秒，两条连接 | 441.5 / 311.6 ms | 1.8 ms |
| 同期 WSS 60 秒 | 682.7 / 2271.2 ms | 1.9 ms |
| 同期 QUIC 60 秒 | 591.3 / 527 ms | 2 ms |

这排除了“尖峰必须由魔兽本体触发”的解释。公网对照使用原版 helper，但合成端直接连 helper 的本地 WebSocket，并非完整 GUI→本地 TCP→魔兽路径。

这两条 QUIC 对照连接的客户端 qlog ACK RTT 中位数分别约 67.1 / 60.44 ms，p99 为 95.57 / 85.61 ms，最大约 132 ms；传输层却分别将 928/3209、894/3185 个 1-RTT 发送包判丢，包含大量 stream 数据。日志中未见这些 packet number 后续被确认。该比例是 QUIC 丢包判定比例，不能直接当作双向物理链路实际丢包率；没有服务端对应 qlog，方向归因仍有限。

这支持“受损传输及按序恢复等待”解释应用延迟明显高于已确认包 RTT。不能将不同统计窗口的最大值相减，以声称得到了精确的某段处理时间。

## 发现并修正的代码问题

`gamewire.Link.Send` 原先先阻塞写可靠 stream，写完后才 `copySender.offer` 快速修复副本。可靠写入恰好卡住时，当前帧副本不能及时进入独立发送器；之前副本还会在 150 ms 后过期。此顺序降低了拥塞期间副本的救援能力。

候选改为先提交预算内的副本，再执行可靠写入。副本发送仍异步、预算仍受限，W3GS 内容、序号、去重、按序交付和现有 wire 协议保持原样。大于 512 字节的帧依旧只走可靠流，此修复不覆盖所有大帧停顿。

新增可控阻塞测试把可靠 writer 保持阻塞，通过真正的 copySender 调度及接收侧 Merger 验证当前帧副本可在 250 ms 内提供恢复：旧顺序失败，候选通过。Go gamewire/BBR 测试通过；候选 Windows helper 的四项协议集成测试通过。

Linux 独立网络命名空间另做一次每方向 5% 随机丢包、50 ms 单向延迟、500 个变长帧的比较：

## 补齐后续定位手段

在源码桥接层增加被动测量：接到原有 W3GS PING 到从本地游戏读到同 stamp 的 PONG 的耗时；另记录 worker 事件循环最大延迟、写队列长度。它不产生额外游戏包，不读取聊天内容。超过 100 ms 的本地回应单独记录，普通统计每 5 秒记录，保留有界样本。

该诊断可以区分“游戏/本地桥接处理慢”和“包尚未穿过公网传输到桥接层”，但当前正在使用的 r9.5 包不具备此新测量，不能倒推本局精确分段耗时。三项测试覆盖匹配 stamp、样本上限和真实 TCP 对端延迟回应。

后续优化应以可靠流大帧阻塞、修复副本覆盖率及双方端到端时间线为重点。需要在可重复丢包/乱序实验中证明尾延迟收益，并检查有序动作与同步校验，不能仅继续切换拥塞控制名称或调低显示值。
