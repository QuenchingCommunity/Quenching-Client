# 匹配通道接入与验收记录（2026-10-27）

## 当前结论

聊天与昵称修复已上线，仍使用原匹配节点、30 ms 发帧，线上实例 `e4fd02cc-4e82-4d14-963e-6ee22d585334`。本次新增了可选 QUIC 侧车、客户端辅助进程和自动探测，但**抗尖峰效果尚未验收，不替换现有 WSS 游戏连接**。

独立 r9.3 连接诊断预览包默认只在开局前探测香港节点的 QUIC，之后仍通过 WSS 开局。预探测不使用玩家票据。既不要求用户改路由器，也没有要求关闭任何防火墙。旧 r9.2 不需要更新即可使用已上线的聊天和昵称修复。

## 已完成的工程接入

- 原地图、位置、两人撮合、游戏时序与结算流程保留。Node 游戏主机仍负责鉴权、校验和真实对局生命周期。
- Windows Go 辅助进程经回环 WebSocket 连接现有原生桥，Linux 侧车经固定回环 WSS 连接现有节点。客户端票据通过连接传递，不出现在命令行或诊断中。
- QUIC 使用 TLS 1.3、系统信任根与域名验证、ALPN `quenching-match-wire-v2`；没有禁用证书验证或使用实验 CA 作为生产信任。
- 每方向独立序号，原 W3GS 封包按最多 256 字节分片，按总长度和偏移精确重组。可靠流传递所有内容；原包不超过 512 字节时，另发送最多四个历史分片的数据报副本。
- 预探测不连接匹配上游、不消耗票据，探测失败可以用原票据走 WSS。实际提交后不假装支持中途续局或用已使用票据换连接。
- 乱序窗口最多 4096 个记录、等待重组内容最多 256 KB，加上单帧最多 65535 字节；拒绝畸形数据、冲突副本、错位/残缺分片。正常关闭有可靠结束标记及确认。
- 诊断包向原有服务器接口上传 `transport-wss-fallback` 或 `transport-quic-probe-ok`，不需要普通玩家看错误码。游戏内保持正常聊天与昵称行为。

## 已通过验证与边界

41 项 Node 测试通过（包括 4 项真实套接字接入测试），8 项 Go 测试通过。新增覆盖：两个协议客户端的建局/加载握手、中文昵称、盟友文字、操作同步、正常退出；UDP 不可达与证书不可信时回退；只探测成功后仍以原票据用 WSS；错误票据、重放票据不抢占有效连接；变长封包及最大 65535 字节封包完整性。

生产服务器本机通过其正式域名与证书连接自己的 UDP 443，两个协议端完成完整流程，对局 `057ce9a6-94f6-4fc7-aed3-2ec540d31c35`，聊天输入 7、转发 5、协议错误 0。这是**服务器自身地址的协议验证**，不是跨公网或两份真实魔兽验收。[证据](evidence/matchmaking-quic-wire-server-self-20261027.json)。

开发电脑通过正式公网入口、实际预探测失败后，用原票据走 WSS，完成昵称、全体/盟友/定向文字、操作同步、正常退出，对局 `9c6fd054-143b-4cc9-b82b-6d7eae5da449`。[证据](evidence/matchmaking-quic-wire-public-compatible-20261027.json)。该测试使用预览包中实际的 Windows 辅助进程；原生控制界面没有参与，不能声称真实地图已验收。

预览包的 81 个文件逐一核对大小及 SHA-256，两份 ZIP 完整性通过；使用包内运行时检查 worker 启动、房间列表、导出与退出协议，报告中没有玩家访问令牌。该 GUI 协议检查使用明确的 QA 模式，并非实际加入对局。[打包证据](evidence/matchmaking-quic-wire-package-20261027.json)。

## 丢包对照：没有通过延迟验收

实际辅助进程运行在两个隔离 Linux 网络命名空间，100 ms 注入往返延迟、双向独立 0/1/5% 随机丢包；每种条件每通道 400 个变长 W3GS 形状封包，包含 8 KB 包与最大 65 KB 尾包。全部有序且内容一致。没有修改公网网卡、线上匹配服务或系统 TCP 参数。

最终限制大包副本后的结果如下；不是实际香港到玩家网络延迟：

| 双向各自丢包 | WSS P95 | QUIC P95 | WSS 最大 | QUIC 最大 |
| --- | --- | --- | --- | --- |
| 0% | 101.4 ms | 102.0 ms | 428.1 ms | 336.4 ms |
| 1% | 170.7 ms | 171.6 ms | 526.6 ms | 921.4 ms |
| 5% | 324.0 ms | 293.2 ms | 670.5 ms | 1714.0 ms |

5% 条件下超过 200 ms 的消息从 107/400 变为 79/400，但 1% 没有稳定优势，大包尾部仍明显退化。**不能以 P95 的局部改善宣称问题解决或默认启用。**[最终完整结果](evidence/matchmaking-quic-wire-netem-20261027.json)。

研究过程中还测试了全量分片都复制：冗余造成更差的拥塞，5% 条件 P95 1149 ms、最大 7159.7 ms，已弃用该策略；[保留失败记录](evidence/matchmaking-quic-wire-netem-rejected-all-copies-20261027.json)。[较早未分片版本的复测](evidence/matchmaking-quic-wire-netem-unfragmented-20261027.json)同样未显示可靠的大包优势。没有拿最早较好的小样本替换后续退化结果。

下一步需在维持顺序和可靠尾部的前提下重新验证副本的带宽预算、拥塞控制竞争和大包调度，分别比较典型对战小包与 RPG 大包压力，再通过实际跨家庭线路验收。原有独立 64 字节小包研究只能说明一种机制可行，不能代替这里的真实封包接入验收。

## 公网 UDP 排查

新机仍为 `191.40.41.124`。UDP 443 服务已监听、UFW/nft 对应允许规则已检查；没有发现 ens18 的 XDP 或 tc ingress 过滤器。用户提供的雨云截图为“不使用安全组”、黑名单模式、空规则，界面明确说明未丢弃端口默认开放；没有理由要求用户改成白名单或关闭防火墙。

多轮开发电脑发出的 UDP 443、24443 探测未在 ens18 抓到，服务器自己通过域名和正式证书的 QUIC 探测成功。开发电脑能收到 UDP DNS 响应，但这不能证明到特定服务器的所有 UDP 路径可用。目前不足以确定是玩家网络、运营商路径或机房入口的问题，需要另一条独立公网线路对照。没有直接把责任归到任何一方。

排查还发现此电脑的系统 HTTP/HTTPS 代理指向本机 Clash 4444，TUN 为关闭状态。Python urllib 默认会使用该代理，所以其 HTTPS 抓包不能直接作为与直连 UDP 同路径的对照。实际 Node WSS 验证使用显式目标和正常 TLS，没有更改用户代理设置、DNS、IPv6 或 Network Guard。

系统已有 TCP BBR、SACK、RACK/early retransmit，无需把重复开启这些配置当成新增优化。QUIC 日志提示 UDP 缓冲上限较小，该点尚需单独受控验证；本次未盲目修改全局 sysctl。
