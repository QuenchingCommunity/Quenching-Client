## 玩家实际更新流程

1. 启动后的现有检查只请求小型签名发布索引。资源版本读所选 `_retail_`／`_ptr_` 的 `_patch/keep.que`；3.4 沿用三个哨兵目录的轻量识别。客户端版本读应用版本。不遍历玩家目录，不用完整性清单猜版本。
2. 沿用现有的合并更新提示，显示当前版本、最新版本；玩家同意后才准备更新。两者都更新时，先资源，再客户端。
3. 读取当前版本的官方文件清单和最新版本的官方文件清单，按路径、大小、SHA-256 比较。比较的是发布元数据，不要求玩家目录和标准包完全一样。
4. 只下载最新清单中新增或内容变化的文件。没有逐版本安装，也没有“超过六版必须重装”的新协议限制。同一个文件改过多次，只下载最终内容；改回原样时，已经拥有原样的旧版本不需要下载它。
5. 文件从签名索引指定的源下载；失败时换下一个源。新协议可描述 GitLawb 分片和 GitHub Release 整文件备用，两者拼接／下载后都校验大小和哈希。
6. 资源更新沿用受影响文件备份、应用、版本标记提交及异常回滚。随后走现有资源设置重新应用流程。客户端则先暂存，退出旧进程后由独立助手替换、重启、等待健康确认；失败则回滚。

缺少资源包的玩家仍手动领取完整包。新协议不承担完整包首装下载，也不是“扫描整个游戏目录并恢复标准配置”的修复器：被玩家自行删除或改动的、官方两版之间未变化的资源，不会被自动遍历检查和恢复。

## 文件删除和客户端二进制

- 不能依据“最新清单中没有”删除玩家目录或文件。MOD 只有明确签名列出的退役文件才有删除资格，并且必须属于该玩家当前版本的官方清单，磁盘内容还必须匹配已知官方旧哈希。改过的文件保留。
- 客户端同步不删除额外文件。它只替换允许的应用／资源路径；Electron 核心变化仍需新的便携包。发布工具在同一内核下发现核心文件变化时也会拒绝生成自动更新候选。
- EXE 和 ASAR 成对暂存／提交。如果其中一个已是目标内容，就直接使用本地文件，不重复下载。只有待更新的文件才读取当前实际哈希。
- EXE／ASAR 可有匹配某个旧哈希的可选 zstd 差分；不匹配、缺少 zstd、下载或重建失败，都回退到该文件的新整文件。不会再因为差分基线不同就只能重下整个客户端。整文件仍必须校验目标哈希。
- 更新成功后，新的官方客户端清单作为同一事务的一部分保存为 `resources/assets/updater/client-files.json.gz`；资源清单保存到所选分支 `_patch/qmf-版本.files.json.gz`。首次没有本地官方清单时，可下载签名索引指定的小型旧版清单。

## 上游发布准备

私有发布器在 `_irys/build-file-sync.mjs`。整个 `_irys/` 继续忽略 Git；签名私钥不进入客户端、仓库或下载产物。此文件只保存在当前发布工作区，克隆公开源码不会带上它。

测试与正式、不同产品各维护独立 `--store`。其中官方小型清单及历史文件哈希账本保留；文件对象是可重取的大缓存，确认 URL／哈希可用后可按需回收，不整删账本和小快照。资源内容通过 Git commit/tag 追溯，不按版复制完整旧树。历史清单每版一份，不是为每对版本生成补丁。

首次迁移优先读取已签名索引对应的小型官方清单 `--seed-snapshot`；若只能从旧包恢复，则从已记录 URL 按需取得、验哈希并临时用 `--seed-root`、`--seed-version` 生成，不要求保留完整旧正式解压树。MOD 另带 `--seed-sequence`；客户端可带旧 `--seed-runtime-version`。不要用玩家已配置的目录当发布基线。没有任何正式旧版基线时工具拒绝生成，避免意外上传初始完整包。

参数（需填实际路径，以下是说明，不是已经发布的命令）：

```text
node _irys/build-file-sync.mjs
  --product quenching-mod 或 quenching-client
  --root 最新正式资源目录或 Windows win-unpacked 目录
  --version 实际版本号
  --display-version 对外版本号（可选）
  --sequence MOD 的递增发布序号（MOD 必填）
  --runtime-version Electron 实际版本（客户端必填）
  --output 本次独立候选目录
  --store 该产品的持久发布缓存目录
  --url-base GitHub Release 的 download/tag 根地址（可重复，顺序即备用顺序）
  --chunk-url-base GitLawb 分片的下载根地址（可重复）
  --seed-snapshot 旧版官方清单.gz（首次，后续可省略）
  --private-key 发布机现有签名私钥路径
```

GitLawb 分片默认 16 MiB，可用 `--chunk-size` 设置。大文件的签名记录先引用分片源，再引用 `--url-base` 整文件备用。小文件和清单只使用 `--url-base`：若还需要 GitLawb 提供它们，把其小文件下载根地址也作为 `--url-base`。GitHub 必须是 Release asset URL，不是 Raw Content。

客户端可以额外提供 `--delta-base 按需取得且已验哈希的旧EXE-ASAR目录 --zstd 发布机的zstd.exe路径`，只为 EXE／ASAR生成有收益的可选差分；缺省不生成差分，按变化整文件更新也能工作。基线不同的其他版本仍用清单比较和单文件补全，不需要为它们额外生成差分。

发布器只扫描官方输入，输出：

- 最新完整文件元数据 gzip，以及每个支持的旧版本的元数据 gzip。
- 需要提供给旧版本的、以完整 SHA-256 命名的 `.bin` 文件对象。所有支持的旧版本都已有相同内容的普通资源不输出；EXE／ASAR额外保留整文件用于基线不符回退。
- 可选 GitLawb 分片与 EXE／ASAR 差分。
- `mod-sync-manifest.json` 或客户端 `latest.json`：Ed25519 签名的小型发布索引。

发布工具会考虑曾新增、曾删除又恢复、内容改回旧版的情况。已记录的同一个实际版本不能换成不同内容再发布，应增加内部版本／发布序号。对外显示版本可保持不变。

把候选对象、旧清单、最新清单和可选分片分别上传到对应产品的源，实际下载核对签名、大小和哈希，然后测试真实便携客户端。现有只针对旧 `.qdelta` 命名的上传脚本不能不检查参数就直接套用新目录。备用 R2 若使用私有 Worker，须先适配文件对象路径、授权与限流；本轮没有修改 Worker 或验证线上 R2 文件同步。

全部验收后才部署新的索引端点：

- MOD：`/api/quenching/mod-sync-manifest.json` 和 `/quenching/mod-sync-manifest.json`。
- 客户端：`/api/quenching/client-manifests/latest.json` 和 `/quenching/client-manifests/latest.json`。

继续保留现有 MOD 清单及客户端 `/client-manifests/3.5.0.json` 等 schema 1 地址给已经分发的旧客户端；不要用 schema 2 覆盖旧端点。已分发的旧代码不会因服务器换清单就自动支持新协议，必须通过它原有的兼容更新先获得新代码，或手动换一次客户端。macOS 自更新范围没有扩大，仍手动替换便携包。

## 2026-10-05：zstd 错误码 31 的路径兼容修复（尚未发布）
